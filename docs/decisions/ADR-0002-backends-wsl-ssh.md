# ADR-0002 · 第一版只做 WSL + SSH 双后端

- 状态：**已修订**（2026-10-26 两次：交付顺序 + 双向隧道；2026-10-30 一次：WSL 反向通路定档。共三次，见文末「修订记录」）
- 日期：2026-10-19

## 背景

ZCode 的远程向导提供 SSH / WSL / Docker 三种方式。调研中 `@jk-uzi/dsh-multi-remote` 也做了三种后端。

但用户明确：**只需要 SSH 和 WSL，不需要 Docker**。

## 决策

v1 只实现 WSL2 与 SSH 两个后端；底座抽象（`Transport`/`Backend`）保留第三个后端的扩展位。

## 理由

1. 用户场景（Windows + WSL + 远端 Linux 主机）已被两个后端覆盖。
2. Docker 的通道模型差异大（Engine API / exec / cp），会显著拉长工期与测试矩阵。
3. 先窄后宽：两后端做好再评估是否加 Docker。

## 实现要点

| 维度 | WSL | SSH |
|---|---|---|
| 连接 | `wsl.exe -d <distro>`（本机进程） | OpenSSH 语义（私钥/agent/密码/跳板） |
| **正向隧道**（本机→远端 dsh） | **M1 实测后定档（2026-10-30，见文末第三条修订记录）：`wsl.exe --exec` stdio 桥为默认，`mirrored` 下 loopback 直通为优化，宿主网关档退役** | `ssh -L`（同一条连接） |
| **反向通路**（远端→本机凭据代理） | 同正向：**默认 stdio 桥**；`mirrored` 下 loopback 直通当优化。反向通路不依赖网络模式 | `ssh -R`，**与 `-L` 挂同一条连接** |
| 认证 | 无 | 私钥/agent/密码 + known_hosts TOFU |
| 引导 | 发行版内装 Node+dsh（缓存可复用） | 远端装 Node+dsh（按平台/架构） |
| 特殊风险 | 发行版未启动、systemd 缺失、路径大小写、**网络模式（NAT/mirrored）只决定优化档 ① 能否启用；默认 ③ stdio 桥不依赖网络模式**（见第三条修订记录） | config 解析（`~` 展开、`.pub` 误配）、ProxyJump、防火墙、**`AllowTcpForwarding no` 会拒绝 `-R`** |

## 后果

- 抽象层必须把「隧道」做成可空能力，而不是所有后端都假设有隧道。
- **抽象层必须把隧道建模为「双向」而非「单向 `-L`」**（2026-10-26 修订，见下方修订记录）。`Tunnel` 接口暴露 `forward`（本机→远端）与 `reverse`（远端→本机）两个能力位，`reverse` 的实现由后端自选（SSH：`-R`；WSL：stdio 桥为默认、mirrored 下 loopback 直通为优化，网关档已于 2026-10-30 退役，见文末第三条修订记录），上层只消费统一的 `reverseEndpoint`。
- 验收：两个后端都要过 A1–A8；SSH 允许在 M2 补齐。

## 修订记录

### 2026-10-26 · 交付顺序改为 WSL → SSH → Docker

**改的是什么**：不是「v1 只做两个后端」这个决策本体（v1 仍然不交付 Docker 可用链路），而是**Docker 的位置**——从「不做，只留扩展位」改为「**最后做，M5 交付**」。

**触发**：用户 2026-10-26 明确「我们先做 WSL 再做 SSH，docker 为最后做」。

**改动**：

| 项 | 原 | 现 |
|---|---|---|
| 交付顺序 | WSL / SSH 并行，Docker 不做 | **M1 WSL → M2 SSH → M5 Docker** |
| Docker 的 UI | 不出现 | 四选一里**灰显「计划中 M5」** |
| Docker 的代码 | 无 | 后端枚举含 `docker`，`create-backend` 显式抛未实现（A11） |
| 接口形状 | 留扩展位 | 照抄 ZCode `SourceServerTransportAdapter`：`probe / createFileTransfer / installOrUpdate / ensureDaemon / openChannel / exec / cancel / dispose` |

**理由（保留原有的三条，并补充）**：

1. 用户场景（Windows + WSL + 远端 Linux 主机）仍由 WSL2 + SSH 覆盖——所以 Docker 仍排最后，不是提前。
2. Docker 的通道模型差异大（无 sshd、无 `forwardOut`、只能 `docker exec -i` + stdio 桥），且上传不能用 `docker cp`（会保留宿主 UID/GID，非 root 容器用户随后无法 chmod）。工期与测试矩阵仍是最重的一条。
3. 先窄后宽：两后端做好再评估是否加 Docker——这条现在有了具体时间点（M5）。
4. **补充**：用户希望 Docker 最终可用，只是不着急。留接口位而非留一句「以后再说」，可以让 M5 接入时**不改上层契约**（ConnectionManager / UI / 投影零改动）。

**连带影响**：

- `requirements.md` §5 非目标第 1 条已改；新增 A11「Docker 接口位」；
- `architecture.md` 新增 §14「后端矩阵与交付顺序」；
- `milestones.md` 新增 M5（1–2 周，排在 M4 之后）；
- `ADR-0005` §决策 4 记录了接口位的具体形状。

**未变**：v1（M1–M4）不交付 Docker 可用链路；抽象层「隧道可空」的后果仍然成立。

### 2026-10-26 · 隧道从「单向 `-L`」改为「双向单连接」（修 R1-1 阻断项）

**改的是什么**：隧道的能力模型。原设计逐字写 `Tunnel：SSH -N -L`，且 `architecture.md` 第 9 步要求「模型请求在远端发起 → 走本地回环代理」——`-L` 的方向是**本机→远端**，这两条在 SSH 链路上互相矛盾。

**触发**：上一轮 R2 终审把 R1-1 立为 **🔴 P1 阻断项**（契约 Constraints 3「凭据不出本机」在 SSH 后端不可达），放行前提第 1 条即要求补反向通路并分链路写明差异化实现。

**改动**：

| 项 | 原 | 现 |
|---|---|---|
| SSH 隧道 | `ssh -N -L <port>:127.0.0.1:<远端端口>` | 同一条连接挂 `-L`（本机→远端）+ `-R <远端端口>:127.0.0.1:<本地代理端口>`（远端→本机） |
| WSL 隧道 | 「不需要，localhost 转发」 | 三档探测：distro loopback（mirrored 才通）→ 宿主网关 → `wsl.exe --exec` stdio 桥；全失败**硬失败** |
| 抽象接口 | 单一「隧道」能力位 | `forward` + `reverse` 两个能力位，上层只消费统一的 `reverseEndpoint` |
| 失败语义 | 未定义 | 不允许退化成「把真实凭据写进远端」；降级链尽头是硬失败 + 可操作提示 |

**证据（2026-10-26 实测，Windows + 隔离 sshd 实例）**：
- `-R 18800:127.0.0.1:18899` 后，sshd 侧 `127.0.0.1:18800` 监听，`curl` 打到本机代理并返回预期 JSON；
- `-L` 与 `-R` 挂在**同一条** `ssh` 连接上同时可用，两侧流量各自命中——**单通道原则不受威胁**；
- 本机 WSL 为 `networkingMode = mirrored`，distro 内直打宿主 `127.0.0.1` 可通；但默认 NAT 模式下不通（网关档在本机因 `192.168.2.1` 未监听该端口而失败），故三档探测是必需的。

**连带影响**：
- `architecture.md` §1 组件图、§2 第 5/9 步、新增 §7.0、§8.3 注记已同步；
- 风险表新增「`AllowTcpForwarding no` 拒绝 `-R`」一行；
- M1 的 WSL 任务新增「网络模式探测与三档降级」验收项；M2 的 SSH 任务新增「`-R` 建立与降级」验收项。

**未变**：仍然只做 B 型；仍然「凭据不出本机」；`-R` 仍绑远端 `127.0.0.1`（`GatewayPorts no`），不对外暴露。

### 2026-10-30 · WSL 反向通路定档：③ stdio 桥为默认，② 网关档退役

**改的是什么**：WSL 后端反向通路的**档位定位**。原设计把三档写成「依次尝试」，未说明哪一档是主线；M1 实测后发现 ② 在本 ADR 的安全前提下不可用，若仍按「依次尝试」实现，会让实现者去调试一个不可能成立的分支。

**触发**：M1 的 WSL 闭环 spike（`spikes/m1/wsl-closed-loop/`，复跑 `node spikes/m1/wsl-closed-loop/probe.cjs`）。A5 断言实测：distro 打宿主网关 `198.51.100.1:18899` 与 `198.51.100.254:18899` 均 `curl: (7)`——**代理只绑 `127.0.0.1` 时网关 IP 上没有监听者**。反证复跑（本条断言的机械入口）：`REBIND=0.0.0.0 node spikes/m1/wsl-closed-loop/probe.cjs` 会把假代理改绑通配地址并新增一条断言，实跑输出 `PASS REBIND 反证成立：代理已绑 0.0.0.0:18899，逐个探测 13 个宿主非回环 IPv4（203.0.113.234, 172.26.192.1, 169.254.96.137, 169.254.89.253, 203.0.113.99, 169.254.63.211, 169.254.113.124, 192.168.1.10, 169.254.123.128, 169.254.255.167, 169.254.207.221, 198.51.100.5, 169.254.27.73）与 2 个默认网关（198.51.100.1, 198.51.100.254）—— 共 15 个目标全不可达` —— 即**绑通配地址也不通**（⚠️ 绑通配 ≠ 绑具体网卡地址，后者未测；见改动表 ② 行与下方证据段）。**这条命令会在宿主 18899 上开全接口监听**（内容是假代理数据），复跑后进程即退出，不要在生产网段长期跑。

**改动**：

| 项 | 原 | 现 |
|---|---|---|
| 默认通路 | 未指定，字面「依次尝试 ①→②→③」 | **③ `wsl.exe --exec` stdio 桥为默认**，不依赖网络拓扑与 `mirrored` |
| ① mirrored 直通 | 三档之一（隐含前提） | **优化项**：探测到通则用，不通不影响可用性 |
| ② 宿主网关 IP | 三档之一，失败即继续 | **不采用/已退役**：只有把本地代理绑到宿主网卡才可能成立，而那违反「绝不把代理端口绑 `0.0.0.0`」的安全约束（**注意：「必须绑网卡」是推论、未实测**——机械复跑只覆盖了一句：绑 `0.0.0.0` 后**探针枚举到的 15 个目标**（13 个宿主非回环 IPv4 + 2 个默认网关）全不可达（`REBIND=0.0.0.0 node spikes/m1/wsl-closed-loop/probe.cjs`，逐目标原始结果见该次输出）。「绑通配地址」**不等于**「绑某块具体网卡地址」，后者从未测过：既未证明能通，也未证明不能通。② 的退役由**安全约束**支撑，不由可达性支撑）。**复活条件（两条都要，缺一不可）**：<br>① 先在真实 NAT 机器上证明「绑某块**具体**宿主网卡地址后，该地址从 distro 可达」（本 ADR 从未测过，绑通配 ≠ 绑具体网卡）；<br>② 再裁决「绑具体网卡是否被允许」——本节安全约束禁的是**通配 `0.0.0.0`**（`architecture.md` §7.0 安全约束条），绑单块网卡并不落在该禁令的字面范围内，**是否放行属未决事项、需人类裁决**；若裁决为不允许，则须先修改该安全约束的范围。**在此之前 ② 保持退役**，不得以「换个 IP 就能通」为由实现它 |
| 两级 dispose | 未表态 | 实测成立：杀 Windows 侧 `wsl.exe` 句柄即回收 distro 侧子进程，**不需要** `wsl --terminate` |

**证据（2026-10-30 实测，Windows 11 + WSL2 `ubuntu_dev`，`.wslconfig` 为 `networkingMode = mirrored`）**：
- ①：distro `curl 127.0.0.1:18899` 通，P50 ≈1.5 ms（20/20）；
- ②：网关两个候选全 `curl: (7)`；`REBIND=0.0.0.0` 反证跑（命令见上方「触发」段）逐个探测**该次运行枚举到的全部宿主非回环 IPv4 + 2 个默认网关**（本机实测为 13 + 2 = 15 个），全部不可达（本机 13 个宿主 IPv4 的失败形态分列：**11 个 `curl: (7)` + 2 个 `curl: (28)`**，探针按退出码分列打印，不折叠成「统一超时」）——但「绑具体网卡地址是否可达」**未实测**（绑通配 ≠ 绑网卡）。目标集合随机器而变，断言覆盖的是「枚举所得」，不是任意宿主地址；
- ③：distro 侧中继监听随机端口、经 stdio 桥回宿主代理，P50 ≈3.5 ms（20/20）；两尺寸线性拟合（每尺寸 5 次取最小）固定开销 `a₃` **5–25 ms/请求**、边际带宽 **30–47 MiB/s**（观测样本落在 30–44，含一次 44 的越界样本，故上界不取样本最大值而留一档余量；① 侧在本次全部轮次里都高于 ③——**这一条只是本次若干轮的观测，非穷尽结论**；折损 **≤1.7×**，最好时几乎无差、最坏约 −40%）⇒ **代价在每请求，不在每字节**。**这是多轮重跑的观测区间，不是统计置信区间**：① 侧外推截距在 −4～13 ms 之间跳动（可正可负），相除得到的「固定开销倍数」会从 <1 跨到几十倍，甚至为负，故此处**不承诺任何倍数**，只承诺上列两个绝对量区间与「代价在每请求」这一不变量（多轮重跑全部成立）。

**理由**：
1. 可用性不能依赖 `mirrored`——它需要 Win11 22H2+（<https://learn.microsoft.com/windows/wsl/networking#mirrored-mode-networking>），且用户 `.wslconfig` 不在我们控制内；
2. ② 与安全约束互斥，留着它只会让实现者以为「换个 IP 就能通」；
3. ③ 的代价形态明确（见上方证据段），**按观测区间最坏端口径（固定开销 25 ms/请求、边际带宽 30 MiB/s；对直通侧本轮最好观测 ~60 MiB/s 约 −50%）评估仍属可接受数量级**；注意「固定开销倍数」这一说法已被撤回（外推截距落噪声，除出来会跨 1.7×～19×），判断改用绝对量。仍需在 M1 实现后用真实模型流量复核一次；
4. 「依次尝试」的语义仍保留 —— 只是顺序变成「③ 为主，① 通则优先」，② 从尝试链里移除。

**连带影响**：`architecture.md` §7.0 表格与新增 M1 实测段、§14 后端矩阵 WSL 行、风险表 WSL NAT 行已同步；`milestones.md` M1 任务表的验收口径改为「默认 stdio 桥」。

**未变**：仍然只做 B 型；仍然「凭据不出本机」；仍然**绝不**把本地代理端口绑 `0.0.0.0`；**硬失败**语义不变——只是判定条件随档位定档收窄为「默认通路（③ stdio 桥）起不来且 ① 不通」，② 不再计入（它已被移出尝试链，把已退役档位算进「全失败」等于让实现者等一个永不到来的分支），提示文案同步改为「无法建立到宿主凭据代理的反向通路」，仍不允许静默降级。
