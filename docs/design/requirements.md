# 需求

> 一句话：**在 Windows 上打开 DSH，选择一台 WSL 发行版或 SSH 主机，像打开本地项目一样打开远端目录；agent、插件、会话、文件全部在远端，GUI 只有一个。**
> 状态：v0.1（2026-10-19，调研完成后的需求基线）

## 1. 背景与用户原话

- 用户在使用「WSL 工作区」类插件（A 型）后发现：**WSL 里为 dsh 装的插件/工具用不了**。
- 实测 `dsh-remote-explorer`（B 型）后判断：**能做到宿主在远端，但不够丝滑**（独立页面、首次连接重、环境不共享、账号面板报错、两套历史）。
- 结论：需要一个自研的 B 型插件，且必须把「集成体验」做到接近 VS Code Remote / ZCode / Zed。

## 2. 目标用户

| 用户 | 场景 |
|---|---|
| Windows 上做 Linux 开发的个人开发者 | 项目依赖、工具链、插件都在 WSL 里；想在 DSH Desktop 里直接开发 |
| 有多台远端机器的开发者 | 代码/依赖在服务器上，本地只做界面；需要与本地工作区混用 |
| 团队/受管环境 | 凭据不能落到远端；需要可审计的连接、版本可控的远端运行时 |

## 3. 用户故事

1. 作为开发者，我在侧栏点「添加远程工作区」，选 WSL 发行版或 SSH 主机，填/选配置，看到连接进度，最后选一个远端目录 → 该目录以一个**远端工作区**出现在侧栏，和本地项目并列。
2. 我打开这个工作区新建会话，agent 的 `bash`、文件读写、搜索、终端**全部在远端执行**；我能在会话里看到远端路径。
3. 我在远端原本就有一套 DSH 环境（`~/.dsh`、插件、技能、settings），我可以选择**复用它**，而不是被迫用一套隔离的空环境；也可以选择隔离或显式同步。
4. 首次连接时我能看到分阶段进度（探测/下载/安装/启动/隧道），可以取消；第二次连接**秒级**进入。
5. 连接断了（网络/休眠/远端重启），侧栏工作区显示状态，我点重连即可恢复；远端进程不会变成孤儿。
6. 我的 API key / 账号 token **永远不出本机**；远端只能看到占位令牌。
7. 远端不可用、版本不匹配、目录不可写、没有 Node 时，我得到**明确的分阶段错误**和可复制的日志，而不是静默回落到本地执行。

## 4. 验收标准（产品基线）

任一里程碑交付前，以下每条都要有真机证据（WSL + SSH 各至少一轮）：

| # | 验收项 | 判据 |
|---|---|---|
| A1 | 原生入口 | 远端工作区出现在**本地侧栏**，带主机标识；与本地工作区同一套列表/会话/标题/历史 |
| A2 | 宿主在远端 | 远端存在 `dsh` 宿主进程；会话的模型请求由远端进程发起；关掉本地 GUI 不影响远端会话数据 |
| A3 | 远端插件可用 | 远端已装/同步的插件（如 hindsight）在远端会话里**真的注册了工具/钩子**（不是只看到文件） |
| A4 | 环境可选 | 「隔离 / 复用远端 `~/.dsh` / 显式同步」三档至少两档可用，且状态可见 |
| A5 | 首连体验 | 有分阶段进度与取消；已引导目标二次连接 ≤ 5s（不含远端启动） |
| A6 | 凭据边界 | 远端进程环境/磁盘中只有占位令牌；真实 key 仅在本机；抓包/日志可证 |
| A7 | 断线恢复 | 网络中断/远端重启后，工作区状态可见、可一键重连，远端进程可回收（不留孤儿） |
| A8 | 失败可诊断 | 每阶段失败有结构化错误码 + 可复制日志 + 重试入口；不出现「远端不可用却本地执行」 |
| A9 | 双后端 | WSL2 与 SSH 两条链路都达到 A1–A8（允许 SSH 在 M2 后补齐） |
| A10 | 版本兼容 | 声明支持的 DSH 版本矩阵；升级宿主后跑兼容检查，不兼容时拒绝并说明 |

## 5. 非目标（v1 明确不做）

1. **Docker** 后端（用户明确不需要；架构留扩展位即可）。
2. 完整 IDE 能力（Monaco/LSP/调试器）。
3. 多人协作 / 共享会话。
4. 纯 headless 部署（无本地 GUI）。
5. 不做 A 型（远端执行）插件；如将来需要，作为可选「world 后端」，不作为主形态。
6. 不做任意云厂商/Codespaces 的专用适配（SSH 能到就行）。

## 6. 约束

- 目标宿主：DSH Desktop 0.2.x（至少 0.2.0-rc.2 / 0.2.1-rc.2 两线），dsh web profile 兼容。
- Windows 本机 + WSL2；SSH 目标为 POSIX（Linux/macOS）。
- 远端需要 Node + dsh（由我们安装或复用），版本对齐规则由我们定义。
- 不修改 DSH 内核代码；只用已文档化的扩展点；内核缺口用「兼容层 + 明确降级」处理。
- 凭据安全：不把 `.credentials.yaml` 复制到远端。

## 7. 体验基准（「丝滑」的定义，量化）

| 指标 | 目标 |
|---|---|
| 首连（已有远端 dsh/Node）| ≤ 10s 到「可选目录」 |
| 首连（需要安装远端运行时）| 有进度、可取消；安装体积与时间**可见**；同一目标二次连接免安装 |
| 打开工作区 | ≤ 2s 出现于侧栏；会话创建后首个命令 ≤ 3s |
| 断线重连 | 自动重试 + 状态可见；手动重连 ≤ 5s |
| 错误信息 | 阶段化（探测/安装/启动/隧道/会话）+ 可操作下一步 |

## 8. 待用户确认（M0 前）

1. **环境策略默认值**：默认「复用远端已有 `~/.dsh`」还是「隔离 + 同步」？（用户诉求倾向复用，但复用有版本/污染风险）
2. 是否需要**自动同步**插件/技能（逐条勾选 vs 全量镜像）？
3. 是否需要支持「多个远端工作区同时在线」？
4. 是否需要「远程工作区也能被 `remote_control`/手机端」访问（后续特性）？
