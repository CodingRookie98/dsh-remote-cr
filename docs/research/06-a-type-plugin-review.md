# 参考实现 A 评估：哪些能吸收、哪些不能

> 2026-11-18。对象：一个成熟的 **A 型（远端执行）** SSH 远程插件，v1.2.0，MIT。
> 只在本机保留工作副本（本地排除，不入库、不进历史）。结论先行：**架构不吸收（与 ADR-0001 冲突），工程与运营实践有 8 条值得抄**，其中 4 条建议 0.4.x 内落地。

## 1. 事实基线

| 项 | 参考实现 A | 我们 |
|---|---|---|
| 形态 | **A 型（远端执行）**：21 个 `rw_*` 工具 + 本地镜像同步 + SFTP | **B 型（宿主远端）**：远端跑完整 DSH，本地只投影 |
| 分发 | npm 发布，带 `--provenance` | GitHub tag / 本地 link，`private: true` |
| 代码 | 纯 JS 入库、无构建；约 4k 行浏览器端 + 34 条路由 | TS + 双 tsconfig，`lib/` 是构建产物 |
| 测试 | 165 个测试文件 + 9 个测试脚手架（假 webServer / 假 SSH / 真渲染） | 676 条 `node --test` + CDP 预览 harness |
| 文档 | 20+ 页：排查手册、测试体系、自愈、迁移指南、参考手册、终端面、统计 | 调研 + 设计 + 决策 + 计划 + 审查归档 |
| 运营 | 主页站、博客、Discussions、用量统计页、SECURITY / CONTRIBUTING / CoC / SUPPORT | 无社区文件，无统计页 |

## 2. 值得吸收（按性价比排序）

### P0-1 社区标准文件（成本 1h）

对方有 `SECURITY.md` / `CONTRIBUTING.md` / `CODE_OF_CONDUCT.md` / `SUPPORT.md` / `PUBLISH.md`，我们没有。
**为什么现在做**：投稿评审的维护者会读仓库；「远端执行任意命令」这类插件的安全声明是硬需求。
**落点**：仓库根新建 4 个文件；`SECURITY.md` 写清我们的安全模型（凭据不出本机、远端只持占位令牌、路由只答回环）——这正好是 B 型的差异化卖点。

### P0-2 排查手册 + 错误码索引（成本 3h）

对方有面向用户的排查手册，每条「已修问题」带根因故事，README 里还有速查段。
我们有 66 个结构化错误码（`locales.ts` 的 `err.*`），却**没有任何用户可见的码表** —— 用户看到 `remote/port-in-use` 只能翻代码。
**落点**：`docs/troubleshooting.md`，正文手写 6~8 条常见症状，末尾附**自动生成的错误码表**（从 `locales.ts` 抽 `err.*` 与 `errNext.*`，脚本 `scripts/gen-error-index.mjs`，CI 校验不漂移）。

### P0-3 文档图片门禁（成本 2h）

对方有静态检查：扫 README / 站点里的所有图片引用，判三条 —— ①文件存在；②可解析 PNG 且尺寸 > 200×150（防占位图）；③覆盖率（README 至少一张，防「全删了」）。
我们刚换过 README 图，这类断链**只会在有人点开时才发现**。
**落点**：`scripts/check-doc-images.mjs`（读 PNG IHDR 取宽高，不依赖图像库），接进 CI 与 `pnpm check:docs`。

### P0-4 README 呈现细节（成本 30min）

三处值得抄：
1. **维护者与链接行**：`由 @X 维护 · 主页 · 统计 · 博客 · 讨论区 · Issue · English` —— 一眼知道找谁、去哪问；
2. **每功能一张截图**，用 `<img src="…raw.githubusercontent…" alt="…" width="1200"/>`：**绝对 URL** 才能在包页/镜像站显示，`width` 控制版式；
3. **「本地也能用」这类对照段**：先给一个零配置的上手路径，降低尝试门槛。
**落点**：README 顶部补维护者/链接行；截图改绝对 raw URL + `width`；补一段「不装远端也能先看面板」。

### P1-5 测试分层文档 + L6「不变量」（成本 4h）

对方的测试文档开头是一份事故复盘：**803 条测试全绿，三个功能不可用**。结论是缺两层脚手架 —— 可复用的宿主测试台（假 webServer + 隔离 `DSH_HOME`）与真 SSH 服务端；于是定了 L1 纯函数 / L2 模块 / L3 路由 / L4 工具 / L5 界面 / **L6 不变量**。
这与我们八轮审查抓到的假绿（夹具与线上形状脱节、用例走不到分支、门禁不看 `title`）是**同一类病**，药方已经有人写好了。
**落点**：`docs/design/testing.md` 把我们的 L0–L3 写清（已有实质：单测 / 路由直调 / CDP harness / 真机探针），并补 **L6 不变量**三条：
- 打开面板不得触发任何远端副作用（只读契约）；
- 每条失败路径必须带 `code` 且至少一条 `nextActions`；
- 字典键在两种语言里必须同集（已有 `locales.test.ts`，提升为不变量条目）。

### P1-6 启动脆弱性静态闸门（成本 2h）

对方的静态闸门专查「会让整个宿主起不来」的注册约束：他们把斜杠命令命名成带点号的 id，框架硬校验 `^[a-z][a-z0-9_-]*$`，结果**整个 DSH Desktop 无法启动**，只能手工修。
我们的同构风险点：`cordis.patch.yml` 行 id、工具名全局唯一（AGENTS §3 记过 `remote_connect` 撞名）。
**落点**：`scripts/check-boot-constraints.mjs`：①patch 行 id 合法且不与已装 profile 冲突；②我们注册的工具名不与 DSH 内置名集合相交；③`package.json#dsh` 三件套齐全。接进 CI。

### P1-7 安装体检 / 自愈入口（成本 3h）

对方提供 `self-heal`：读已装 `package.json` 版本，从 tarball 重新铺文件树并报告变更数。
我们的历史事故是同一类：**`lib/` 曾被 ignore 排除，导致 v0.1.0 从 GitHub 装上去缺入口**（见 `docs/release/OPEN-SOURCE-CHECKLIST.md` §2）。
**落点**：`lib/doctor.js`（`node lib/doctor.js` 可跑）：校验 `files` 清单里的入口是否存在、`lib/client.js` 是否为空、`dsh.engines` 是否满足当前 DSH、迁移标记是否可写；输出可粘贴报告。自愈（重新下载）留到 0.5。

### P2-8 发布自动化与覆盖率

- 对方的发布流程：**推 tag 即发布**（全门禁 → npm 发布 → 从 CHANGELOG 抽段生成 Release → 装一遍 tarball 验证）。我们不发 npm，但「tag → 门禁 → Release 正文从 CHANGELOG 抽」可以直接抄。
- 对方的覆盖率合并脚本提醒我们：**我们至今零覆盖率数据**。先给单测接 `c8`，再谈跨套件合并。

## 3. 明确不吸收

| 项 | 理由 |
|---|---|
| **A 型架构**（21 个远端工具 + 本地镜像同步 + SFTP） | 与 [ADR-0001](../decisions/ADR-0001-host-on-remote.md) 直接冲突：A 型结构性地给不了「远端已装插件可用」「关窗任务继续」这两件事 |
| IDE 三栏布局 | 不是架构冲突，是产品取向差异；0.4.0 刚重做完两级主从，短期再上一套布局会稀释「单一原生 GUI」的定位。记为可选后续 |
| 终端面（TUI）集成 | 与 B 型远程开发无关 |

## 4. 对方踩过、对我们直接有用的三个坑

1. **远端执行工具曾完全绕过本机 `sandboxPolicy`**（后来才补）：A 型结构里「远端执行」天然脱离本地沙箱；我们是 B 型，远端宿主跑自己的策略 —— 这一点应写进 README 的「为什么需要它」，作为结构优势而不是口号。
2. **SFTP 一次超时会把整条通道拖成永久超时**（后来修）：我们 SSH 侧有看门狗与实例回收，但**没有**「一次超时即置死通道 + 重建」的显式语义；0.5 的传输层值得补。
3. **注册约束违规会让整个宿主起不来**：见 P1-6。

## 5. 建议的落地顺序

| 顺序 | 事项 | 成本 | 依赖 |
|---|---|---|---|
| 1 | P0-1 社区文件 + P0-4 README 呈现 | 1.5h | 无 |
| 2 | P0-3 图片门禁 + P1-6 启动约束闸门 | 4h | 无 |
| 3 | P0-2 排查手册 + 错误码索引 | 3h | 错误码已稳定 |
| 4 | P1-5 测试分层与 L6 不变量 | 4h | 无 |
| 5 | P1-7 `lib/doctor.js` | 3h | 无 |
| 6 | P2-8 发布自动化（tag→Release） | 2h | 需先决定是否打 GitHub Release |

## 6. 说明

评估对象只在本机保留工作副本（本地 `info/exclude` 排除），仓库与提交历史里不出现其名称与地址；本文所有比较只保留结论与做法，不含对方源码。
