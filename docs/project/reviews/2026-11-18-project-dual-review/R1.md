# R1 红队 + 第一性原理审查 — dsh-remote-cr @ 2270c71（Full 模式，插件项目）

### 1) 结论

**不可签：2 条阻断。** 功能主干（差集/逐条隔离/optout 落盘/两侧 runtime 门禁/错误信封/迁移）经代码与变异验证成立，安全面（四处 shell 拼接、回环+围栏、体上限、abort 真杀子进程）**未发现破口**；但「同一 target 的两条写路径无互斥」与「『用哪份远端 dsh』在两个解析器里优先级相反」会把**一次成功的安装打到错误的安装目录并回报成功**，属于错误行为 + 用户被误导，必须在放行前修掉。

### 2) 阻断项（Blockers）

**B1｜同一 target 的宿主升级与插件同步没有互斥，UI 也允许同时发起**
- `src/local/plugin-sync/service.ts:112-121`（`applying` 集合）与 `src/local/api/routes.ts:624,718-729`（`upgradingHosts` 集合）是**两套独立锁**；`src/client/components.ts:791` 的 `sync-apply` 只按「已选条数 / no-runtime」禁用，**不看** `hostUpgrade.phase`；同文件 `:837` 的对齐按钮却在 `running` 时禁用 → 只有一侧设防。
- 伤人点：升级执行体（`host-upgrade.ts:104`）是对 `<staging>/npm` 做 `npm install --global`，它重写的正是插件同步要执行的那份 `dsh`（`apply.ts:56-59` 用同一 prefix 的 `npm/bin/dsh`）。用户在升级进行中再点「同步选中项」，就会在 npm 重写 `lib/node_modules/@deepseek-ai/dsh/**` 的同时用该 dsh 跑 `plugin add`；后果是两条都报失败、profile 可能半装（可重跑，非不可恢复，但属于环境损坏窗口 + 假失败）。
- 验证：`grep -n "applying" src/local/plugin-sync/service.ts` 与 `grep -n "upgradingHosts" src/local/api/routes.ts` 可见两个 Set 无交集；`routes.test.ts:404`、`service.test.ts:183` 只覆盖各自单侧，**没有任何跨锁用例**（这是 Test Gap，不是设计说明）。
- 归属：**本次交付引入**（宿主对齐 81bf722 新增第二条写路径）。

**B2｜「远端用哪份 dsh」两个解析器优先级相反：检出优先 vs staging 优先**
- 连接侧：`src/local/backend/ssh/runtime.ts:124,201` —— 先探 `<remoteRoot>/apps/cli/lib/bin.js`，探到就用检出，否则回落 staging（日志原文「检出：… 里没有 apps/cli/lib/bin.js，改用引导器装到 staging」）。
- 同步侧：`src/local/plugin-sync/read.ts:59-60` —— READER 先用 `~/.dsh-remote-cr/staging/*`（且取 `readdirSync` 的 **`dirs[0]`**，**完全不接收 target/anchor id**），只有 staging 一个都没有时才看 `hint`（`checkoutRoot`）。
- 伤人点：远端同时存在检出与 staging 时，`plan.runtime.source` 报 `staging`、`plan.host.remoteVersion` 取的是 staging 那份，`POST /plugin-sync/host` 就按 `stagingDir = runtime.dshRoot`（`routes.ts:760`）把新版本装进 **staging**；而重连后真正跑的是 **检出**。于是：每次点「对齐」都回 `{version, restartRequired:true}`（用户看到「已装到 x」），重连后 `sync-host` 依旧 `align` → 无出口的成功循环；同一条错位也让 `apply` 用「不匹配版本的 dsh」去写 profile。多个 staging 目录时 `dirs[0]` 还可能选到废弃目录，等于把宿主装到没人用的目录并报成功。
- 验证：上述两处代码路径直接对照（`runtime.ts:124/201` vs `read.ts:59/60`，`read.ts:59` 无 target id 入参）；`read.test.ts` 只覆盖「同一次读取里带出版本」，没有任何「既有检出又有 staging 时该选谁」的用例。
- 归属：`dirs[0]` 属**既有技术债**（WSL 同步 5b7a53a），但「以它为目标做宿主升级并回报成功」是**本次交付引入**（81bf722）。

### 3) Suggestions（非阻断，按影响排序）

1. **契约声明的 `profile` 参数被代码忽略**：契约 §2 允许 `GET/POST /plugin-sync` 带 `profile`，`routes.ts:639-649` 只留了 `...(syncOptions.profile === undefined ? {} : {})` 的死展开，profile 恒取后端配置（`web`）。非 web profile 的用户会读/写错 profile，且无任何提示。**本次引入**（死代码是新写的）。
2. **applying 态「逐条进度」是假的**：`routes.ts:700-705` 调 `applySyncPlan` 时**不传 `onResult`**，服务端钩子（`apply.ts:104`）无用；`panel-view.ts:301-307` 是拿到完整响应后再循环 setState。契约 §4「逐条显示进行中与结果」未兑现——3 条 × 180 s 上限内界面只有一个「同步中…」。
3. **一个错误码背三种语义**：`remote/plugin-sync-unsupported` 同时用于「已在同步中」（`service.ts:117`）、「已在升级宿主」（`routes.ts:720`）、「host reject 原因」（`routes.ts:742`）。而 `panel.ts:357-362` 会用字典覆盖 detail，于是并发/拒绝时用户看到「请求里包含不可同步的插件 / 只勾选可同步项后重试」——真实原因被吞。建议拆码或让 detail 优先。
4. **`PATH='.':$PATH` 把远端 cwd 放进搜索路径**：`apply.ts:54` + `wire.ts:211`（SSH 无 runtime 时的 `nodeBin: '.'`）。同文件注释担心的是 `PATH=''`，但写法本身就把 `.` 前置了；远端 home 里任何一个叫 `dsh` 的文件都会优于真 dsh 被执行。建议改为不加 PATH 前缀。
5. **`parseInstalledVersion` 只认标记前一行**（`host-upgrade.ts:66-72`）：任何多出来的 stdout 行（npm notice、dsh 的告警行）都会把**一次成功的安装**判成「自报版本不符」，用户只能反复重试同一个假失败。建议向上扫描最近一条 semver。
6. **预览 harness 的覆盖与强度**：实际 23 场景（`pnpm e2e:preview` 输出「截图 23 / 23」，而计划文档写 24/24）；`sync` 对话框的 **`failed` 态没有场景**（`preview-fixtures.mjs:300-519` 无 `sync-failed`），契约 §4 也只列五态。`requireMarkers`（`preview-wizard.mjs:973-977`）只判「计数 ≥ 1」，不断言文本与禁用态；禁用态靠组件级测试兜住（见 M3），但预览层对「同步按钮在 no-runtime 时禁用」无断言。
7. **契约 §1 类型清单滞后**：`skip-official`、`reasonDetail`、`remote-read-failed` 在 `shared/plugin-sync.ts:18-26` 都不存在（官方包被直接跳过、无 detail 字段）。照契约实现 UI 会等一个永不出现的 action。
8. **文档计数漂移**：`README.md:166`「含 66 个错误码索引」，`pnpm check:errors` 实际 **71 条**；契约 §4 五态 vs `sync-state.ts:64-75` 六态（多 `failed`）。
9. **`SYNC_REASON_KEYS.none → 'syncReason.missing-remote'`**（`sync-state.ts:9`）语义错位，目前靠「up-to-date 组不渲染 reason」偶然兜住；一旦渲染就是假原因。建议给 `none` 独立键。
10. **optout 非原子写**（`optout.ts:27-31`）：两个面板并发写会丢 target；`writeFileSync` 截断窗口内读到空 → `readOptout` 静默当空，静音「自己失效」。
11. **状态根名硬编码**：`wire.ts:124` 写死 `.dsh-remote-cr/sync-optout.json`，未用 `migration/legacy-names.ts` 的 `HOME_DIR_NAME`；再次改名时会漏。
12. **测试缺口（M4 证据）**：「静音后接入不自动弹」这条需求**零覆盖**——把 `panel-view.ts:263` 的 `plan.muted ||` 删掉，全量 790 条**仍然全绿**。建议把自动弹窗判定抽成纯函数并断言。
