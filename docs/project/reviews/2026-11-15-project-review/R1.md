# 第一轮对抗审查报告 (Round 1 Red-Team Review Report)

## 1. 第一性原理与本质溯源分析

- **审查基线与方法**: master@8278d2b..HEAD（feat/add-workspace-ui-v2，24 提交，未合并）；判定口径取交接单 §6（阻断 = 拿不到结果 / 写坏状态 / 失败显示成成功）；先跑门禁看退出码，再用 node 直接驱动纯 reducer 取现场，最后回到源码行核对——文档结论一律按未验证处理，独立复跑后才采信。
- **改动性质定性**: 主体是「本质根因修复 + 架构演进」，但在失败面上留有**浅层修补**（同一类缺陷只修了一半）。
  - 本质修复：W1–W4 四条根因（routes.ts:169 的 wslAvailable 语义、UTF-16LE 诊断落在 stdout、browse.ts 只看 stderr、无发行版仍发本机请求）都在因果层被改写，不是把红字换成人话；diagnosis.ts 用「标记优先 + ASCII 占比 + 干净度」做**确定性双解码择优**（diagnosis.ts:49-63），失败归类只认 ASCII 证据（diagnosis.ts:152-154），本地化文案只进 logTail（diagnosis.ts:117）。这是可复现的机制级修复。
  - 架构演进：从「翻页式四屏」改成「左栏常驻 + 右栏只换内容」的双栏工作台（components.ts:600/659），把「点来源即跳转」拆成 selectSource 与 beginWake 两条转移（state.ts:194/234），并用代次门（navSeq / wakeToken）替代「靠时序碰运气」。方向正确。
  - 浅层修补（本轮主要攻击面，见 §4）：
    1. 「失败要响」只对**轮询**做了（pollError + 重试，components.ts:690-711），对**来源探测**没做：/sources 失败后左栏只剩一行文字、没有任何重试入口（components.ts:604），整张卡不可用。同一类缺陷两种待遇。
    2. 「取消是真的」只对**显式取消按钮**做了（wakeController.abort + 宿主 res.on('close')，components.ts:910-913 + routes.ts:457-467），对**关窗路径**（× / Esc / 点遮罩）没做：关窗不 abort，B1 的宿主 kill 路径不可达。
    3. 「可编辑路径」新增了 browser-path（components.ts:414-431），但提交端的真值仍取 listing.path（state.ts:467），于是**屏幕显示的路径与真正落盘的路径可以是两个**。这是本轮最硬的一条。
- **物理与业务一致性**:
  - B 型约束未被破坏：浏览器半没有任何 node:* 依赖（components.ts 只用 globalThis 窄接口取 clipboard/document），目录列举全部回到宿主半 /teleport/api/list（api.ts:141-146）。凭据面未被触碰（本次 diff 未改 proxy/credentials）。
  - 「单一原生 GUI」仍成立：向导挂在官方 directoryFlow 的两个洞上（registration.ts:49-52、111-125），priority: -1 顶替机制未改。
  - 物理事实与代码一致的部分：wsl.exe 管理输出是 UTF-16LE、--exec 输出是 UTF-8（distro.ts:15-22），真机失败在 stdout 且 stderr 为空（browse.ts:143-177 已按此改）。
  - 物理事实与代码**不一致**的部分（契约漂移）：超时值从 RFC 的 20s 改成 60s（routes.ts:128），码集合从 5 个加到 6 个（shared/api.ts:273 新增 wsl/timeout），但 RFC-0001 §4、ADR-0005 决策 6、ui-design §10.3 三处仍写 20s / 5 码。RFC §10 明文写着「这三个偏差不得静默漂移，要改就改本节并同时改 §4」——本次是**在 §4 之外静默漂移**。
- **过度设计审计**:
  - 必要，不能删：navSeq（state.ts:96-104 + 347/359）与 wakeToken（state.ts:105-112 + 256/282）各自挡住一条已复现竞态；AbortController 两端联动是「取消不是装饰」的唯一实现路径。R2 的结论（删任一即退回阻断项）经本轮复算成立。
  - 属于过度设计的部分：wakeController 是**模块级单例**（components.ts:287），而它服务的是两个可能同时挂载的 slot 实例；正确形态是 per-instance ref。同类的 restoreFocusAfterNav 也是模块级（components.ts:279），单实例下无害、多实例下互相抢。
  - 500ms 定时 measure（components.ts:872）在 `open` 期间常驻，只为一个 layout 断点服务；用 ResizeObserver 或「只在初次 + resize 时量」即可，不值得每秒两次 getBoundingClientRect。
  - 类型逃逸：panel-view.ts:268 用 `as string | null` 强转一次（setActiveSession），属可删的噪声。

## 2. 运行时与客户端/沙盒安全推演

> 本项目是「宿主注入式 client 插件 + 原生 DOM（手写 createElement）+ 宿主模块表提供 react 运行时」，不是 React/Next 应用。下面按实际栈作答，不适用的子项显式标注。

- **渲染/Hook 或等价生命周期约束**:
  - 不适用：本项目无 Next.js、无 RSC、无 SSR、无 hydration；组件不做服务端渲染，因此不存在 hydration mismatch 面。
  - 适用的等价约束（本轮逐条核对）：
    1. hooks 顺序：DirectoryFlow 的 6 个 useEffect/useState 全部写在 `if (!open) return null`（components.ts:879）之前，提前 return 不会造成 hooks 数量漂移——正确。
    2. effect 门控：onPicked 的 effect 按 open 门控（components.ts:780-787），R2-C1 的「重挂重复回传」已修好；但**关窗后异步落地改写 step** 会让 [open] 的 `step !== 'closed'` 门（components.ts:774）失效，见攻击路径 2。
    3. 事件监听生命周期：文档级 keydown/focusin 在 `open` 变化时增删（components.ts:807-848），cleanup 完整；不存在监听泄漏。
    4. 受控输入：browser-path 的 value 来自 store、onInput 写回 store（components.ts:414-425），预览垫片与真机都验过（K2/K3 PASS）。
- **全局可变状态与多实例污染**:
  - 模块级可变单例共 4 个：wizardStore（wizard-store.ts:12）、wakeController（components.ts:287）、restoreFocusAfterNav（components.ts:279）、以及 WIZARD_INITIAL（components.ts:1023，只读用途）。三个 directoryFlow/panel 渲染根共享同一份向导状态，这是「一份状态多处渲染」的刻意设计。
  - 单实例下经源码与 reducer 复核无污染：cancelWake 的代次 +1 使晚到结果被丢弃（复跑结果 cancelThenLateSettle = choose/idle）。
  - 多实例下有两个**未验证**的风险面：(a) wakeController 被后一次 wakeSelected 覆盖，实例 A 的「取消唤醒」会 abort 实例 B 的请求 → B 收到 AbortError → 走 failWake，把「别人取消」渲染成「你的发行版起不来」；(b) [open] effect 的 step 门与共享 store 组合，一个实例关窗会把另一个仍在 open 的实例的 state 改成 closed，该实例不会重新 openWizard（其 [open] 依赖未变）。真机未开过两个洞（交接单 §4.1 自述），故标为未验证。
- **浏览器 API 与降级兜底**:
  - clipboard：走窄接口 globalThis.navigator.clipboard.writeText，拿不到就返回 false（components.ts:215-226），不抛错——降级本身正确。**但所有调用点都丢弃了返回值**（components.ts:924-926、panel-view.ts:639、812），于是「复制日志 / 复制诊断 / 复制 wsl --install」在权限被拒时静默失败，用户以为复制成功。这是铁律 4 的漏点。
  - document/window：全部经 typeof 探测后才用（components.ts:291-300、809-876、861-876），在无 DOM 的 node 环境里不会炸（这也解释了为什么根 tsconfig 能编过）。
  - 无 HTML 注入面：src/client 下 grep innerHTML / dangerouslySetInnerHTML / new Function / eval 命中 0；所有动态文本都走 createElement 文本子节点（自动转义），logTail 与 wsl 原文只作为文本渲染（components.ts:379）。
  - 宿主沙盒：浏览器半只打 /teleport/api/*（api.ts:63），宿主半先问官方 connection 围栏再判回环（routes.ts:350-367，装配见 index.ts:145），跨站请求面没有因为新路由而扩大；新路由 /wsl/wake 的 body 有 64 KiB 上限（envelope.ts:18/90）。

## 3. 红队攻击路径推演 (Concrete Failure Scenarios)

- **攻击路径 1: 路径框里改完没回车，点「添加此目录」——落盘的是上一个目录**
  - **触发条件**: 已进入浏览屏并成功列出过一次目录；用户在路径框里输入/粘贴新路径，未按 Enter，直接点底栏「添加此目录」。
  - **复现推演**: browser-path.onInput → typePath 只改 state.path（components.ts:891-893）→ 底栏 actions-path 显示的也是 state.path（components.ts:941）；点 confirm → confirmPick(state)（components.ts:904-906）→ addInputOf 取 `state.listing?.path ?? state.path`（state.ts:467）→ 提交的是**旧 listing 的 path**。canConfirm 只判 listing 非空、不比对 state.path（state.ts:447-454），所以按钮是可点的。
  - **实测（node 直跑 reducer，非推断）**: 用 listing.path=C:/old/dir 建态后把 path 改成 C:/new/typed，canConfirm=false→true 之间的门没拦住，addInputOf().path 返回 C:/old/dir，divergesFromDisplayed=true。同一状态下「刷新」用的是 state.path（components.ts:898-900）——刷新与提交取的不是同一个真值，用户无法自洽解释。
  - **影响结果**: 把**没有选中的目录**当成工作区交给 owner（createWorkspace 的入参来自 onPicked），即交接单判定口径里的「把错目录放行」。用户会在错误目录上开会话，直到发现文件不对。
  - **涉及代码**: src/client/components.ts:891-893、src/client/components.ts:904-906、src/client/components.ts:941、src/client/state.ts:447-454、src/client/state.ts:466-472。

- **攻击路径 2: 唤醒进行中关掉弹窗——「取消」是装饰，且下次打开直接落在上一次的浏览屏**
  - **触发条件**: 点一个 Stopped/损坏的发行版（进入「正在唤醒…」），在结果回来之前按 Esc / 点 × / 点遮罩关窗。冷启动发行版有 60s 窗口，这不是边角场景。
  - **复现推演**: 三条关窗入口都只调 onCancel（components.ts:977、987、810-828），**没有一处 abort**：wakeController 只在 handlers.cancelWake 里 abort（components.ts:910-913）。于是 (a) 宿主侧 wsl.exe 继续跑到 60s 超时，B1 修的 kill 路径根本没被走到；(b) 结果回来时 settleWake 的 token 仍然匹配（关窗不改 wakeToken），success 分支调 enterBrowse 把 step 从 closed 改成 browse（state.ts:256-279 → 323-334）。
  - **实测**: closeWizard 后喂同 token 的成功结果，afterLateSettleOk = browse/ok；再打开时 [open] effect 判 `wizardStore.get().step !== 'closed'`（components.ts:774）为真 → **跳过 openWizard 与 loadSourcesInto**，界面直接呈现上一轮的浏览屏（已列好上一发行版根目录）。同理，晚到的轮询快照会把 closed 改成 done（实测 afterCloseThenFlowDone = done + picked=C:/tmp），此时重开会让 onPicked 的 effect（components.ts:780-787）立刻带着这个**用户本次没有确认过**的路径回调 owner。
  - **影响结果**: 取消不生效（用户以为关了，机器还在转）；重开向导跳过来源探测、落在旧状态；极端时序下把上一次的路径当成这次的选择回传。
  - **涉及代码**: src/client/components.ts:767-777、src/client/components.ts:780-787、src/client/components.ts:910-913、src/client/components.ts:977、src/client/components.ts:987、src/client/state.ts:256-279、src/client/state.ts:323-334。

- **攻击路径 3: /sources 探测失败——整张卡死路，没有任何重试**
  - **触发条件**: 宿主半 /sources 抛错（wsl.exe 卡住超 15s、宿主重启中、路由 500、网络抖动）。
  - **复现推演**: loadSourcesInto 的 catch → failSources 把 options 置 null、distros 清空、sourcesError=原因（state.ts:189-191、components.ts:137-145）→ sourceRail 在 options===null 时**只渲染一行文本**（components.ts:603-604），没有重试按钮、没有「重新探测」。四个来源全部消失，右栏停在「从左栏选一个位置」。唯一出路是关窗再开（[open] effect 会再调一次 loadSourcesInto）。
  - **影响结果**: 用户在弹窗内拿不到任何结果，且界面不给下一步——与铁律 4（每个失败都要有可重试路径）和 D2 已经给 pollError 做过的处理直接矛盾。可撤销（关窗重开），但可发现性为零。
  - **涉及代码**: src/client/components.ts:137-145、src/client/components.ts:600-604、src/client/state.ts:189-191。

- **攻击路径 4: 浏览阶段发行版挂了——诊断的「下一步」与原文被 UI 层吞掉**
  - **触发条件**: 唤醒成功后发行版在列目录时不可用（vhdx 被拔、WSL 服务重启、15s 列目录超时）。
  - **复现推演**: listDistroDirectory 抛出 TeleportError（code=wsl/*，带 nextActions 与 logTail，browse.ts:171-176）→ 浏览器端 catch 只取 messageOf(error)（components.ts:115-117）→ failListing 存字符串（state.ts:359-362）→ listingView 只渲染这一行（components.ts:454-461）。nextActions、wslCode、logTail 全部到不了 DOM。
  - **影响结果**: 同一个错误在唤醒阶段是完整诊断卡（码 + 人话 + 原文 + 三条出路 + 复制诊断，components.ts:365-388），在浏览阶段退化成一句括号话 + 一个重试。用户遇到 vhdx 失效时看不到「wsl --unregister 会删数据」这类后果说明。
  - **涉及代码**: src/local/api/browse.ts:155-177、src/client/components.ts:111-118、src/client/components.ts:453-461、src/client/state.ts:359-362。

- **攻击路径 5: 两个客户端同时点同一个发行版——第一个取消，第二个收到伪造的「启动失败」**
  - **触发条件**: 同一宿主被两个页面同时操作（两个标签页 / 用户开了 hero 与 sidebar 两个洞），两人点同一个发行版，其中一人取消唤醒。
  - **复现推演**: /wsl/wake 用 wakeInflight 做在飞去重（routes.ts:422、450-468），**共享同一个 AbortController**；A 客户端断开触发 res.on('close') → controller.abort()（routes.ts:457-467）→ 共享的 task 收到 abort，runWsl 杀子进程，close 回 exitCode=null → runInDistroChecked 判非 0 → describeWslFailure 归类为 **wsl/unknown**（实测：aborted 的诊断为 code=wsl/unknown、detail=「启动失败，且 wsl.exe 没有给出可读的报错」）。B 客户端 await 的是同一个 pending（routes.ts:450-453），于是拿到 ok:false + 这条**由别人取消造成的**诊断。
  - **影响结果**: B 的右栏弹出「发行版起不来」的诊断卡，并建议「复制诊断贴到 issue」——一次并发取消被渲染成一次真实故障（失败可见性反向失真）。A 自己因为 controller.signal.aborted 在 sendJson 前 return（routes.ts:470），行为正确；错的是共享的失败没有被区分成 cancelled。
  - **涉及代码**: src/local/api/routes.ts:422、450-475、src/local/backend/wsl/exec.ts:138-155、src/local/backend/wsl/diagnosis.ts:162-171。

- **攻击路径 6: 键盘 / 屏幕阅读器路径上的三个漏点（不阻断，但会让无障碍承诺打折）**
  - **触发条件**: 非浏览屏按 `/`；焦点在 contenteditable 区域按 `/`；读屏用户进入弹窗；焦点在向导外按 Esc。
  - **复现推演**: 文档级 keydown 的 `/` 分支只豁免 INPUT/TEXTAREA（components.ts:813-821），不判 contenteditable、不判 defaultPrevented、不判修饰键；且它先 preventDefault 再查 [data-teleport='browser-path']，该元素在 choose/running/done 屏不存在 → 按键被吞、什么也不发生。Esc 分支（components.ts:823-828）确实在文档级，但 K9 的实际焦点是 entry（.preview/keys-local.json: focusBefore=entry、wizardStep=browse），K10 只在 K9 失败时才跑（preview-keys.mjs:349）——「焦点落在向导外时 Esc 是否生效」这条**没有任何断言**。弹窗根节点没有 role=dialog / aria-modal / 焦点陷阱，Tab 顺序第一站是 wizard-cancel（K1 visited: wizard-cancel → source×3 → crumb×4 → browser-path，共 9 次 Tab 才到路径框）。
  - **影响结果**: 键盘用户会丢键；读屏用户拿不到「这是一个模态对话框」的语义；Q2 的修复面未被门禁覆盖（属未验证，不是回归）。
  - **涉及代码**: src/client/components.ts:807-848、src/client/components.ts:963-999、scripts/preview-keys.mjs:329-377。

## 5. 第一轮结论概要

**裁决：不通过（3 条阻断：R1-B1 / R1-B2 / R1-B3）。** 三条都不是「换个文案」能收口的：R1-B1 是把未确认的目录写进工作区，R1-B2 是取消无效 + 重开串状态，R1-B3 是失败态没有出路。三条都能用纯 reducer 或 DOM 级证据复现，且都落在本次 diff 新增的交互链路上。

**成立的部分（有价值、且我认为不需要返工）**：
1. WSL 诊断链（UTF-16LE 双解码择优 + ASCII 归类 + 穷举 switch 不留 default）是本轮质量最高的部分：机制正确、有负控、有真机字节夹具。
2. 代次门设计（navSeq/wakeToken 必填）方向正确，且本轮复算证明删任一都会退回已修好的阻断项。
3. 断言面在**代码层**是完整的：ui-design §10.4 列的 30 个既有标记全部仍在 components.ts 里渲染，只增不改。问题在门禁没有全部覆盖它们（R1-8）。
4. 四条已裁定项（B1/B2/B4 + Q1/Q2/Q3 + C1/C2/C3）经复跑与源码复核仍然成立：cancelThenLateSettle=choose/idle、staleSeqRejected=true、onPicked 的 open 门在、receiveFlow 的终态门在。R1-2 是 B1 之外的另一条入口（关窗），不是 B1 复发。
