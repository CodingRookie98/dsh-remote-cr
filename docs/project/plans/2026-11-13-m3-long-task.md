# M3 · 长任务与丝滑（Long Task & Smoothness）

> **文档控制信息**
> - **文档标识**: PLAN-M3-LONG-TASK-2026
> - **当前版本**: V1.0.0
> - **文档所有者**: Lead
> - **生效日期**: 2026-11-13
> - **前置**: M1（WSL）与 M2（SSH）已于 2026-11-13 **有条件签署**（见 [签署归档](../reviews/2026-11-13-m2-exit-signoff/README.md)）

## 0. 结论先行

1. **M3 只做一件事：让「长任务」这条场景成立。** 依据 [生态与价值评估](../research/05-ecosystem-and-value-2026-11.md) §10：DSH 插件市场 8 个远程插件全是 A 型且零安装，我们在「远程开发」这个位置上赢不了；唯一的结构性优势是**远端宿主**——它换来的就是「断网/关电脑后任务还活着」。
2. **先修状态机，再加功能。** M2 的五轮 R1 已证明取消/连接生命周期的组合面是缺陷温床（D7 至今未闭合）。长任务会把「长时间驻留 + 多次断连重连 + 取消」叠加，状态机不形式化，功能越多越不可维护。
3. **不做的**：Docker 后端、插件同步（`sync` 档）、完整 IDE。它们不服务长任务，且 M5 之前没有收益。

## 1. 范围与非目标

| 做 | 不做 |
|---|---|

## 3. 任务分解

### M3-1 取消状态机形式化（1–2 天）

**状态**：`S0` 无连接、`S1` 已连（live=A）、`S2` 留存（detached=A）、`S3` 接入中（attach≠∅）。

**事件**：`attach(T)`、`cancel`、`connect-ok(B)`、`connect-err`、`rehandshake-ok`、`rehandshake-err`、`disconnect`、`recycle`、`transport-lost`。

**不变量**（每条都要有单测）：

| # | 不变量 | 当前状态 |
|---|---|---|
| I1 | `live` 与 `detached` 不持有同一个 connection | M2 已修（D1） |
| I2 | **已 dispose 的 connection 不得出现在任何槽位** | **D7 违反** |
| I3 | `cancel` 后回到「接入前」的 `(live, detached)`，或更安全的状态 | 部分（D7/D8 的边界） |
| I4 | `attach` 结束（成功/失败/取消）后 `attachProgress === null` | M2 已修（D6） |

**做法**：
1. 把 `ProjectionService` 的连接槽位操作收敛成 3 个原语：`shelve(entry)`（live→detached）、`install(entry)`（设为 live）、`drop()`（dispose 并清空），**所有**槽位变更只走这三个。
2. 每个原语维护一个 `Set<RemoteConnection>` 的「已 dispose」标记（`#retired`），`install`/`shelve` 拒绝已退休对象 —— 这条直接封死 I2，不依赖「值快照 vs 引用」的推断。
3. 用表驱动测试：状态 × 事件 → 期望的 (live, detached, attachProgress) 与不变量。

**验收**：D7 夹具转红；新增「所有槽位变更都经过原语」的静态断言（grep `#live =` / `#detached =` 仅出现在原语内部）。

### M3-2 长任务（1–2 周）

**事实（2026-11-13，`spikes/m3/long-task.ts` + `measurements.long-task.json`）**：

| 问题 | 实测 | 结论 |
|---|---|---|
| 关掉本地 GUI 后，远端会话数据还在吗 | `dispose()` 后 60 s 重新接入：`sessionKept:true`、24 条会话、workspace id 不变 | ✅ **已成立**（顺带闭合 A2 的未验证项） |
| 关掉本地 GUI 后，远端 dsh 还在跑吗 | `dshAliveAfterWait:false`、`portBusyAfterWait:false` | ❌ **不驻留**（看门狗按 A7 的约定回收） |
| 远端 nohup 的裸任务还在吗 | `longTaskAlive:true` | 不依赖 dsh 的进程本来就能活 |

⇒ 拆成两片：**M3-2a 会话数据持久（已达成，补证据即可）**；**M3-2b 驻留模式（待做）**——后者才能让「agent 驱动的任务」在关电脑后继续跑。

**M3-2b 的设计要点（待评审）**：① `keepAlive` 配置：本地正常退出时向看门狗发「保留」标记，而不是 EOF 退出；② 远端实例登记 `~/.dsh-teleport/instances/<id>.json`（端口 + token），下次接入先探测复用；③ 与 A7「不留孤儿」的冲突要写清：驻留模式**必须**有 TTL（例如 30 min 无重连自动回收）与显式「结束远端」入口，否则 A7 的保证被它推翻；④ 实例探测失败（进程已死）要能回落到正常启动。

1. **断线续跑的语义**：宿主重启 / 网络中断后，重新接入同一 target 时，**远端会话与正在跑的任务仍在**（远端 dsh 未被看门狗杀掉的前提下）。需要：`DSH_HOME` 复用档（默认）、看门狗不因短暂断连退出、重连后会话列表按 id 复用。
2. **后台任务可见**：面板列出远端会话的「正在运行」状态与最后活动时间；关掉本地 GUI 不影响。
3. **验收（真机）**：`关宿主 5 分钟 → 重开 → 接入同一 target → 会话与任务仍在，且 id 不变`；断网注入（拔网/防火墙）后自动重连，不需要手动点。

## 5. 风险与反向条件

| 风险 | 反向条件 |
|---|---|
| 状态机形式化变成重构黑洞 | 只允许在 `service.ts` 内部改；不改对外 API；D7 夹具必须转红，否则回滚本次改动 |
| 长任务依赖「远端进程不被杀」 | 若真机上宿主退出必然触发看门狗（无法保住远端任务），则把 M3-2 的范围降为「会话数据不丢」而不是「任务不中断」 |
| 发布后无人使用 | 6 个月无真实用户 ⇒ 停功能投入，转官方参考实现（评估文档 §11） |
